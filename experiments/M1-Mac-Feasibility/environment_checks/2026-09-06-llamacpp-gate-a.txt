Configure-time detections (from CMake's own output, not assumed):
  - CMAKE_SYSTEM_PROCESSOR: x86_64
  - GGML_SYSTEM_ARCH: x86
  - "Including CPU backend"; "x86 detected"; CPU backend variant "ggml-cpu: -march=native"
  - "Accelerate framework found" -> BLAS found via Apple's Accelerate framework
    (Accelerate.framework) -- a CPU-only math-library optimization, NOT GPU
    acceleration. Enabled by CMake's own default on macOS; left as-is.
  - "Could NOT find OpenMP" (warning only, non-fatal) -- OpenMP was not available;
    the build proceeded without it.
  - No Metal, OpenCL, CUDA, or Vulkan backend was configured or built (explicitly
    disabled Metal via -DGGML_METAL=OFF; none of the others were requested).

Build result: SUCCESS. `cmake --build` completed with no errors; all targets
including `llama-cli`, `llama-server`, `llama-quantize`, `llama-bench`, etc. built.
Total build tree size: ~164 MB (`build/`); full clone incl. build: ~773 MB.

Why `-DGGML_METAL=OFF` was chosen explicitly (not left to CMake's own default):
llama.cpp's own build docs state "On MacOS, Metal is enabled by default" -- generically
for macOS, not restricted to Apple Silicon. This machine's GPU is an AMD Radeon Pro
5300M (a discrete GPU, not Apple Silicon's unified-memory architecture that llama.cpp's
Metal backend is primarily developed and tested against). Per the explicit instruction
not to assume Metal acceleration is available/useful and not to pretend AMD GPU
acceleration exists if it does not, the conservative, reproducible choice made here is
to force CPU-only execution outright (`-DGGML_METAL=OFF`, llama.cpp's own documented
flag "to force CPU execution", `docs/build.md` line 686) rather than leave an untested,
unverified GPU-acceleration path enabled by default. This also matches Track A's
existing framing throughout `READINESS.md` as a CPU-compatible track. No claim is made
here about whether Metal-via-AMD would or would not have worked -- it was not tested,
and is out of scope for Gate A.
